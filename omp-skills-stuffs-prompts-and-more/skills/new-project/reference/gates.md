# new-project gates

this file is the authoritative contract for product decision gates and point-of-risk approvals. phase skills prepare artifacts, return their hashes, and return compact `gate_handoff` data. `new-project` presents every product gate, renders the recorded artifact paths and hashes followed by the handoff's ordered `presentation` lines and `warnings`, records each product-gate decision in its matching gate record in `.factory/state.json`, and writes `.factory/state.json`. no phase skill may present a product gate or infer approval from an artifact on disk.

## gate-1 decision authority and audit context

the `thesis` gate record in `.factory/state.json` is the sole authoritative gate-1 decision input. `new-project` writes the exact closed enum, timestamp, checked artifact hashes, and verbatim user note there. `.factory/decisions.md` is append-only audit context: it retains decision history, is never approval authority, and never grants, proves, or replaces approval.

`new-project` appends user and product-gate decisions to `.factory/decisions.md`. `factory-taskgraph` may return contract decisions for that append-only record. no other phase writes gate decisions there, and no phase reads `.factory/decisions.md` as approval authority.

## product decision gates

A product gate is a product choice about the recorded artifact set. It is not permission to perform a separate external effect. For every gate, `new-project` records the exact closed enum, decision time, checked artifact hash or hashes, and any verbatim user note in `.factory/state.json`. A changed checked hash invalidates that gate's artifact and every stage named in its boundary. A phase skill prepares and reports; only `new-project` presents and writes the product gate record.

The closed state schema has no separate `terminal-revision` value. When a terminal product decision requires a status change, use the existing `cancelled` status and preserve the exact decision enum in the gate record and audit note. A fresh root may use the supported restart/new-root admission only after residual tasks, worktrees, effects, and approvals are reconciled. The new root must establish its own source, hashes, breakpoint attempts, and gate records; it must not copy an old approval, invent a resolver, or treat an old artifact as approved merely because its bytes are unchanged.

## point-of-risk approvals

These approvals are separate from product gates. Before the action, verify user authority for its exact operation and target; existing authority persists through phases and owners. Ask only when authority or a material risk decision is missing. A product decision does not authorize unrelated external work.

The admitted native factory protocol also requires a matching risk/disclosure response bound to the exact request. Preserve that mandatory record; do not fabricate a native response from general earlier prose. Replaying the same committed effect preserves its original identity and response and must not repeat the external action. A distinct request uses its own deterministic identity; changed payloads never reuse an existing effect key. If the native contract requires a new response, obtain that response through its supported owning-session path, explaining that protocol requirement rather than claiming the user's prior authority expired. A changed target or operation beyond existing scope needs new authority; a changed worker, phase or lease alone does not revoke it.

| action | state.json gate enum | classification | show before asking |
| --- | --- | --- | --- |
| public network research | `research-permission` | **not a gate** | the search scope, and that the idea text leaves the machine |
| `gh repo create` | `repo-create` | **not a gate** | owner, repository name, visibility, source directory, remote name, and whether it pushes |
| any `git push` | `push` | **not a gate** | remote, branch, and commit count |
| publishing, releasing, or changing visibility | `none` | **not a gate** | the exact operation, target, and parameters; use a fresh native request because no dedicated state enum exists |
| deleting a worktree or a branch | `worktree-cleanup` | **not a gate** | the path, whether it is merged, and the exact cleanup operation |
| any credential use | `none` | **not a gate** | which credential, target, operation, and parameters; use a fresh native request because no dedicated state enum exists |

When the enum is `none`, the protocol still requires its matching native risk response and a recorded decision in the run log; `none` means only that `state.json` has no dedicated enum for that action. Repository creation, pushing, publishing, cleanup, and credential use remain independent approvals even after any product gate is approved. An acknowledged or unknown external outcome remains uncertain: do not resend automatically to recreate a receipt; preserve the exact request and resolve it through the owning native session's recovery path.
