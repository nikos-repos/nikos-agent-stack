# Session coordination

Deliver an accepted result through existing native OMP and stack interfaces. Reuse authoritative records and a small task contract; do not create a capsule hierarchy, world model, queue, approval service or second execution store.

## Establish the contract

State the outcome and owning root, exact source/input revision, writable workspace/scope, expected artifact and acceptance, resource/stop conditions and material unknowns. A paragraph is sufficient when those facts are simple. A worker receives only its bounded assignment; it cannot expand scope, recursively dispatch a fleet or accept the whole delivery.

For an ordinary defined change, use [engineering-workflow](../engineering-workflow/SKILL.md). Use [new-project](../new-project/SKILL.md) when a multi-phase product/specification workflow requires it. Choose that route before admission; never waive a gate or machine contract of an already active factory run.

Use the current user authority for its stated action/target. Ask only for a material missing decision; continue independent authorized work. Native tool approval, product approval, reviewer findings, advisor notes, effect outcomes and delivery gates have different owners.

## Orient or resume

Read current facts through their existing owners:

| Question | Authoritative basis |
|---|---|
| What outcome and who owns it? | Authorized brief, actual host/native session/root and, when applicable, durable run input. A title or worktree name is not identity. |
| What remains active or pending? | Exact native jobs, the full owned durable run/effect tree, required questions and external effects, including residual work beneath a terminal parent. |
| What was verified? | Current artifact/revision, actual check/review evidence and integrated base; a worker summary or resolved_ok is insufficient. |
| What is unknown or blocked? | Missing/stale/conflicting evidence, failed criterion or unresolved decision, with its responsible owner and next useful inspection. |
| What can happen next? | Exact target, prerequisites and existing authority; revalidate with the native/engine owner before acting. |
| What limits apply? | Turns, spend, elapsed time, capacity and retained history separately, each marked enforced, advisory, measured or unavailable. Missing is not zero. |

Present outcome → owner → next action → blocker/age → proof. Keep source/fence/input/cursor details available on demand. A resume packet is this derived view with existing evidence references and read time, not a new durable checkpoint or permission. If a proposed status view or bridge is absent, inspect existing records; do not invent an operator flag or claim a complete fleet inventory.

Preserve raw state meanings. waiting_effect names its outstanding condition; waiting_for_user is a durable breakpoint; blocked needs cause repair; halted and failed are terminal; completed means the process returned its output. The current paused label for halted does not make it resumable. CLI exit zero, gate release with failures and process completion do not prove delivery.

For an explicit time/token budget, preserve its original start/deadline and remaining allowance across resume or handoff. Reserve capacity for required verification and useful closeout. Stop admitting new scope at the applicable limit; preserve incomplete obligations rather than claiming acceptance or resetting the clock. Distinguish advisory discipline from actual runtime enforcement.

## Admit concurrent work

- Each root retains its acceptance and recovery responsibility. Another root admits work only through a discovered native control capability and an explicit accepted handoff within user authority; observation alone supports a recommendation.
- Name one integrator per shared delivery branch and one admitted writer for a shared checkout. Transfer ownership explicitly after inspecting active native jobs and release evidence. Unknown ownership withholds that shared scope; disjoint work can proceed.
- Native task concurrency is session-local; ctx.parallel limits an effect group; engine leases protect a root tree. Report each scope honestly. Known-root capacity agreements are cooperative, not hard global reservations. Strict shared limits require an actual enforcing boundary or confined dispatch.
- Admit only ready dependencies with actual available workspaces/resources and review/integration reserve. Include setup, context, proof, expected retries/rework, maintenance and human opportunity cost when deciding whether a worker or extra isolation is worth it.
- Verify native allocation rather than guessing checkout paths or creating duplicate worktrees. Disjoint files can still collide through Git metadata or a changed base. Current factory task granularity, prescribed workspaces, batch and all-results barrier remain binding unless a matched versioned change is adopted.
- Keep mutation leases operation-scoped and cooperative. Approval waits and parent task coordination do not hold a write lease; delegated writers own their writes. Async terminal/cleanup evidence and root-tree fences remain distinct. External editors are outside that guarantee.

Surface required questions, ready-for-review results and actionable incidents before ordinary progress. Coalesce duplicate progress and keep unchanged state quiet; never hide a critical decision or its deadline. This is attention discipline, not a claim of installed notification middleware.

## Select context and proof

Use a short stable architecture map for orientation and exact current slices for the decision. Run independent reads together and project compact results; keep dependent writes, approvals and adaptive reads sequential. Compare simple scoped search before introducing retrieval infrastructure.

For a consequential derived fact retain query/document/table coordinate, as-of time, method/transformation, uncertainty and source hash or pinned-manifest reference. Direct native facts can link their existing record. A useful retrieval comparison checks recall, citation completeness, table/date accuracy, latency and total cost on the same questions.

Cache only immutable version-bound context. Never inherit current permission, lease ownership, workspace state or freshness from a cached summary. On handoff, check exact identity, pending effects/questions, failed proof and uncertainty against original sources. A compression claim is not evidence.

Use an independent behavioral oracle for acceptance. Another model/reviewer is warranted by the task's uncertainty/risk or current contract, not automatically by every edit. For nontrivial generated work, use relevant withheld/falsifier cases. Preserve failed checks; correct an invalid oracle with sourced evidence and an independent recheck rather than relabeling failure.

## Reconcile before retry

Use [omnipotence-cli](../omnipotence-cli/SKILL.md) for actual durable commands and authoring contracts; use native job controls for ordinary OMP tasks. Do not fabricate durable effects for tasks that never used the engine.

| Situation | Required response |
|---|---|
| Source/input/session/fence mismatch | Recover the original bound evidence and current owner through supported interfaces. Do not reinterpret old state or accept an old attempt's result. |
| Requested effect with both dispatch timestamps null | Only supported engine recovery, after identity checks, may automatically schedule the provably undispatched effect. |
| Intent/acknowledgment present or outcome unknown | Reconcile actual execution. Confirm/fail/retry through existing authority; never resend to reconstruct a receipt. |
| Committed result, interrupted publication or pending hook | Inspect committed identity first. Identical publication is idempotent; conflicting duplicate fails. Retry pending delivery only; reconcile unknown non-idempotent side effects. |
| Detached job or abort with deferred cleanup | Terminal/cancel alone is insufficient for workspace reuse. Require settled cleanup/release and external reconciliation. Keep owner, job/lifetime, attempt/source, workspace and unresolved effects in existing evidence/handoff references. Quarantine has no automatic expiry. |
| Isolated retry while old job unresolved | Admit it only with evidence the old attempt cannot affect the new delivery or duplicate an action; otherwise retry is unavailable while unrelated work continues. Reject late old-attempt results. |
| Questionnaire reset on start/switch/branch | Inspect unanswered requirements and explicitly redeclare when still applicable. Successful ask transport clears transient policy, not answer meaning, consent or a separate breakpoint. |
| Halt, cancel or deadline | Use the exact native/engine owner; preserve residual evidence. Observed advisory deadline stops new dependent admission and escalates/reconciles. Timeout is not proof of cancellation. |

Forever retains unenforced maxturns, runs in a live native host, ends on process return and supplies no detached daemon, hard total-spend cap or retention pruning. New universal TTL, spend or retention enforcement requires its own compatible implementation; do not claim it exists.

## Accept, deliver and retain useful learning

Check the current integration base and artifact, resolve changed seams, and run the proof required by the task and configured gates. Deliver the actual requested behavior/content/format and disclose material residual work. Publishing or another external effect still needs applicable authority.

Promote a verified non-obvious lesson with material future value into its narrowest maintained home, with owner, applicability, source/version, failure/fix evidence and invalidation/retirement trigger. A first severe failure can qualify. For promotion, refresh, or harness comparison, read [learning and evaluation](references/learning-and-evaluation.md). Use a short decision record for consequential alternatives, not every action. An unfamiliar high-risk explanation is advisory unless an explicit bounded authorized task criterion makes it blocking; it is never an extra factory result field.

When refactoring the harness itself, first name the observed ambiguity or delivery burden, current owner, smallest change, affected consumers, acceptance and rollback. Proposed observation, scheduling and factory migrations are independent capabilities. A plan or this skill does not install them or prove a performance gain.
