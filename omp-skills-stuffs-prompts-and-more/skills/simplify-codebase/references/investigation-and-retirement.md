# Investigate a justified retirement

Use for a simplification survey or when a proposed cut depends on claiming that a responsibility or consumer no longer exists.

## Coverage before ranking

For broad scope, orient by owner domains and their entry points, state, dependencies, configuration, and operational boundaries. Inspect relevant domains before declaring the first attractive cut the best opportunity. Report blind spots and inaccessible sources. For focused scope, inspect the affected neighborhood; do not manufacture a whole-repository audit.

Consider units below a file: a schema field, CSS selector, dispatcher branch, persisted state, background producer, dependency capability, or compatibility contract. Smells and static analysis locate candidates; they do not establish safe removal.

## Consumer evidence

Trace static callers and then the consumer classes relevant to this contract: dynamic registration/loading, exported APIs, plugins, generated artifacts, configuration, external callers, persisted data/runs, and release history. Distinguish support/documentation references from executable consumers and unresolved reachability. A zero-result search is only supporting evidence. Unmerged or unshipped code can still have downstream branches, stored inputs, public packages, or external consumers.

For each material cut establish its owner and burden, known consumers, preserved contract, strongest counterargument, consequence if wrong, decisive proof, and remaining unknowns. Account for affected consumers as changed, compatible with evidence, or explicitly outside accepted support. Required consumers cannot be classified away. Unknown consumers stay unresolved until decisive evidence or an authorized scope decision resolves them.

## Compare obligations

Compare what disappears with migration, adapters, wrappers, extra state/configuration, transitive dependencies, release coordination, and ongoing maintenance introduced by the replacement. Assess each cut's independent benefit and coupled prerequisites. Prefer an existing platform guarantee only after checking its exact semantic coverage and residual obligations.

Distinguish borrowed data within one owner from owned data crossing asynchronous, wire, or storage boundaries. Do not remove trust validation, authorization, data-loss protection, accessibility, or recovery merely because the happy path looks simpler. Collapse lifecycle mechanisms only if owner, transition, failure window, and guarantee actually coincide. Use a small reachable-transition table when it clarifies cancellation, partial publication, callbacks after termination, or double cleanup.

Record the strongest reason to retain a candidate and what evidence would overturn the removal. A dependency map may clarify confirmed edges; it is not runtime proof. Use existing visualization capabilities if useful, without adding a renderer stack for the audit.

## Decision history

Before removing current documentation, preserve unique rationale and conditions for reintroducing the retired design. Classify decisions as current, partly displaced, or superseded, and repair current inbound links. Keep immutable history and old run inputs intact. Present code can violate a valid governing rule; do not rewrite the rule simply to match code drift.
