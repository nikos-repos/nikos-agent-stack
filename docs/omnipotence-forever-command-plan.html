omnipotence extension · implementation plan

make forever mean unbounded

this plan turns /omnipotence-forever into an explicit, unbounded extension command. it keeps required safety gates, removes the finite turn stop, skips optional process pauses, and continues through the existing hidden-turn scheduler until the process ends or the operator stops it.

decision

chosen direction

treat persistent: true as an engine rule: do not enforce or extend maxturns. register /omnipotence-forever explicitly, set its optional-breakpoint policy to false, and reuse the durable effect, recovery, and stop paths. do not add a second engine or a daemon.

basis: omnipotence/processes.ts:5-24; omnipotence/engine.ts:727-745; omnipotence/index.ts:290-325

scope decision: “standalone command” means the omp slash command supplied by the omnipotence extension. it does not mean a new binary or host-independent service. the package already loads omnipotence/index.ts as the extension and exposes a separate one-shot cli binary.

source: package.json:29-42; omnipotence/cli.ts:201-242,574-600

target command contract

invocation

/omnipotence-forever <process-id> [json-input] starts one session-bound run with mode forever. the command is the explicit opt-in to unbounded turns.

turn budget

the store retains the finite process maxturns value for replay compatibility, but the engine never blocks or extends a persistent run because of that value.

breakpoints

optional process breakpoints auto-approve. required process breakpoints still wait for /omnipotence-resume. normal omp approval and point-of-risk confirmation remain unchanged.

continuation

external effects continue through hidden next turns. sleep effects use durable timers. restart recovery dispatches safe never-sent work and marks previously sent work uncertain.

termination

the run ends when process code returns, fails, halts, reaches a non-budget safety block, or the operator calls /omnipotence-stop.

completion

forever does not restart a completed process. process code owns repetition and must use deterministic, unique effect keys for each cycle.

host lifetime

host shutdown pauses execution. durable state resumes when omp restores the session. this command is not a daemon.

existing mechanisms: omnipotence/index.ts:163-284,382-485; omnipotence/engine.ts:396-408,683-706; omnipotence/store.ts:1473-1502

02 · replay

03 · continue

04 · dispatch

05 · stop

  • keep execute: true and persistent: true.

make the engine enforce persistent turns

  • apply the budget block only when policy.persistent is false.

  • retain finite behavior for babysit, call, plan, and yolo.

scope limits and risks

kept

safety boundaries

  • required process breakpoints
  • normal omp approvals
  • point-of-risk confirmation
  • uncertain-effect recovery
  • source-drift and hook blocking
  • fences, leases, and explicit stop
source: docs/omnipotence-user-guide.md:253-267; omnipotence/engine.ts:683-725,912-963
not added

non-goals

  • no background daemon outside omp
  • no automatic restart after completion
  • no database migration or infinity sentinel
  • no duplicate forever-only engine
  • no automatic retry after unknown external work
  • no bypass for failures or non-budget blocks
source: omnipotence/index.ts:430-485; omnipotence/store.ts:21-45; omnipotence/cli.ts:574-600
why not store infinity in maxturns?

the public contract and store validate finite integers, and the value remains useful when the same process runs in a finite mode. policy bypass avoids a migration and preserves replay data.

source: omnipotence/contracts.ts:400-429; omnipotence/store.ts:997-1055
why not auto-restart completed processes?

a restart would repeat side effects under a new run without a cycle contract. unbounded turns let the process define deterministic repetition while explicit completion keeps terminal guarantees.

source: omnipotence/engine.ts:741-746; omnipotence/store.ts:1482-1487,1781-1786
what grows during a true forever run?

each unique effect and transition adds durable replay state. replay work and sqlite size grow, and a nonterminal run pins its blueprint version until halt or another terminal result.

source: omnipotence/store.ts:904-930,981-995,1473-1502; omnipotence/blueprints.ts:363-395
what is the main operational risk?

the explicit command removes the turn-budget circuit breaker. a faulty process can consume repeated model turns until stop, failure, or a required gate. one forever root also occupies its session binding while active.

source: omnipotence/engine.ts:727-729; omnipotence/index.ts:338-353; omnipotence/store.ts:1023-1061,1169-1220
