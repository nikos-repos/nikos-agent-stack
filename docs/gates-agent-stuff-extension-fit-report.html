revised technical decision memo · native omp compatibility

keep native task, hub, ask, todo, bash, edit, and write. add one read-only gate tool at most.

the first report proposed a custom child runner. that recommendation was wrong for this harness. native task already provides the required subagent lifecycle and evidence. the useful transfer from agent-stuff is now limited to internal data models: immutable audit scopes, event correlation, durable gate state, and deterministic risk rules.

corrected decision: build the canonical scope engine first. optionally expose it as a net-new read-only gates_audit tool. never register or shadow task, hub, ask, todo, bash, edit, or write. never create a second subagent or process-control surface.

native non-replacement rules

1

consume native evidence

gate-checker may observe tool calls, tool results, structured details, and lifecycle events. it must not rebuild the native runtime behind them.

2

add orthogonal tools

a new tool must have a unique name, a net-new read-only contract, and schema-shaped output. it must not delegate work already owned by another tool.

3

keep policy in hooks

use extension hooks for deterministic checks and evidence capture. do not replace mutation, subprocess, task, session, or approval tools.

safe tool additions

decision: do not build gates_audit yet

the automatic extension and cli can call the same internal scope engine without a model-facing tool. exposing it now adds a second invocation path but no required capability.

unique future benefitthe model could request a deterministic audit of an arbitrary immutable scope before session stop, compare a base or commit outside the current request, and receive compact schema-shaped evidence without reconstructing it from git output.
current benefitlow. automatic session-stop checks already protect delivery, and the cli can support explicit or ci-like audits.
costanother discoverable tool consumes model attention, creates an optional path that agents may call unnecessarily, and risks users treating an early audit as final authorization after the tree changes.
build triggeradd the tool only after a real workflow needs model-selected base, commit, or folder audits during a turn and repeated native git calls prove inadequate.
future boundaryif built, keep it read-only and uniquely named. return the scope digest and exact repository state. do not checkout, fetch, mutate, execute caller commands, spawn agents, commit, or change approval.

verification stays internal

do not create a verify, run_tests, or process tool. keep the current automatic verification until a documented native-compatible execution seam is selected. the final design may consume a successful native bash result, or use the extension execution helper with cancellation. it must not copy the native bash job, output, artifact, timeout, or signal machinery.

revised implementation roadmap

  1. canonical immutable scope engine

    adapt only the scope taxonomy and merge-base resolution from review.ts. share one read-only implementation between index.ts, gate-cli.js, and any future audit tool. start with request-baseline and uncommitted scopes. normalize staged, unstaged, untracked, deleted, renamed, mode, binary, and submodule states. record resolved commit ids and a scope digest. never fetch or checkout.

  2. defer model-exposed gates_audit

    keep the scope engine internal and use it through automatic hooks and the cli. expose a schema-shaped read-only tool only when model-driven audits of arbitrary scopes become a demonstrated workflow. the automatic session-stop checks remain authoritative.

  3. native task provenance adapter

    remove the prose manifest as primary authority when native structured task results exist. consume task call id, native agent id, status, duration, model, structured output, artifact and patch metadata, and lifecycle events. correlate these with the canonical parent scope. keep the text/json manifest only for backward compatibility.

    attribution limit: a shared writable worktree still cannot prove which concurrent actor made a change. use native task isolation when authoritative child-specific patches are required.

  4. native custom-entry gate journal

    use pi.appendEntry with a namespaced custom type and rebuild through one pure reducer on session start, branch, and tree events. persist request, repository, policy, baseline, continuation, failure, verification, and terminal outcome fingerprints. do not port goal mode.

  5. explicit terminal outcome labels

    rename cap and stalemate releases to released_with_failures, never pass. if waivers are later needed, use native ask and bind approval to exact request, failure, repository, and policy fingerprints plus a reason. headless mode returns action_required.

  6. advisory deterministic risk rules

    adapt the taxonomy, not the review workflow, from review.ts. flag migrations, dependency and lockfile changes, authentication and permissions, public contracts, and destructive operations with stable ids and exact diff evidence. default to advisory.

  7. cooperative mutation lease only after evidence

    do not port control sockets or a todo queue. if measured concurrent-session races justify a lease, implement it as internal gate state and use native hub/session liveness. bind it to canonical git common-directory and worktree identity with owner and fencing tokens. it cannot exclude external editors.

explicitly rejected ports

  1. agent-stuff subagent runner

    native task is strictly broader for this harness. tmux children would split identity, cancellation, artifacts, isolation, history, and lifecycle across two systems.

  2. control sockets and process manager

    native hub already owns these capabilities.

  3. replacement edit, write, or bash tools

    they would shadow native bookkeeping and create bypass or time-of-check/time-of-use gaps.

  4. custom answer, todo, fork, review, or prompt-mode workflows

    native tools and session operations already own these workflows. gates should inspect evidence, not become a second harness.

  5. repository auto-trust

    approval and trust policy must remain native and explicit.

  6. model judgment as a gate

    model output can explain evidence. it must not determine pass or fail.

corrected delivery order

phase 1: extract the canonical scope engine. phase 2: migrate extension and cli evidence acquisition to it. phase 3: consume native task provenance and persist native custom gate entries. later, only on measured demand: expose read-only gates_audit. do not build a custom verify runner or subagent tool.
